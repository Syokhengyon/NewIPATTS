## 一、最重要的發現：音素數據不在 wasm 裏

實測 `engine/espeakng.worker.data`（6.5 MB）：

```
450 個文件，文件之間間隙合計 0 位元組   ← 完美緊密拼接
```

索引不是存在 `.data` 裏，而是**內嵌在 `espeakng.worker.js`** 的一段 JSON：

```json
[{"filename":"/usr/local/share/espeak-ng-data/phondata","start":6168141,"end":6735481}, …]
```

| 文件 | 大小 | 內容 |
|---|---|---|
| `phondata` | 567,340 B | **音素合成數據**（Wcmd 指令 + 波形） |
| `phonindex` | 44,114 B | `uint16[]`，索引到 `phondata` |
| `phontab` | 104,850 B | 編譯後的音素表結構 |
| `intonations` | 2,040 B | 語調曲線 |

### 結論

**改音素不需要碰 wasm，也不需要重新編譯 wasm。**
只要替換 `.data`（必要時同步更新 JS 裏那份 JSON 的偏移），
`espeakng.worker.js` / `.wasm` 一行都不用改。

> `phondata` 裏**沒有** RIFF 頭（搜到 0 次），非零字節佔 76.5% ——
> 波形是以 espeak 自己的壓縮格式存的，不是原始 WAV。

提取工具：`tools/extract-espeak-data.mjs`（解到 `reference/espeak-fs/`）。

## 二、espeak-ng 的聲音是怎麼造出來的

依據官方文檔
[`phontab.md`](https://softwarepublico.gov.br/gitlab/vlibras/nvda/raw/fa93d8563083d477ae19288af84bdd8147c25788/include/espeak/docs/phontab.md)：

音素定義寫在 `phsource/phonemes`（**純文本**），每個音素一段：

```
phoneme aI
  vowel
  starttype #a endtype #i
  length 230
  FMT(vowels/ai)          ← 從共振峰參數合成
endphoneme

phoneme s
  vls alv frc sibilant
  Vowelin  f1=0  f2=1700 -300 300  f3=-100 80
  Vowelout f1=0  f2=1700 -300 250  f3=-100 80  rms=20
  WAV(ufric/s)            ← ★ 直接播一個 WAV 文件
endphoneme
```

**三種發聲方式：**

| 指令 | 用途 | 說明 |
|---|---|---|
| `WAV(file)` | 清輔音（p t k f s **θ**…） | **直接播 `phsource/` 下的 22kHz/16bit 單聲道 WAV** |
| `FMT(file)` | 元音、響音 | 從**共振峰序列**生成 |
| `FMT() addWav()` | 濁塞音、濁擦音（b g v z…） | 共振峰合成 + 混入 WAV |

**另有兩個關鍵指令，決定「聽起來像不像」：**

| 指令 | 作用 |
|---|---|
| `Vowelin` | 這個輔音對**後接元音**共振峰的影響（過渡段） |
| `Vowelout` | 對**前接元音**的影響 |

> ⚠ 這一點在第四節很重要：**人耳分辨邊音、鼻音、近音，主要靠過渡段**，
> 不是靠孤立音段的頻譜。

編譯命令（官方）：`espeakedit --compile`
文檔明說：「Vowel files … are made using the `espeakedit` program」。
另見 [espeak-ng issue #23](https://github.com/espeak-ng/espeak-ng/issues/23)。

### 這對你的設想意味着什麼

**你的思路是對的，而且有兩條路比你設想的更直接：**

* **元音 / 響音**（`FMT`）→ **就是共振峰**。扒示範音頻 → 量 F1/F2/F3 → 寫進
  `phsource/vowel/*` → 重編譯。**完全對得上。**
* **清輔音**（`WAV`）→ **更直接**：θ 這種音**本來就是一個採樣文件**，
  換掉那個 WAV 即可，連共振峰都不用扒。

## 三、θ / ð 專題（已實測到底）

### 3.0 起因

使用者問：**「espeak 能發英語就不可能漏 θ/ð，怎麼會完全無法移植？」**
—— 這個質疑是對的，而且推翻了我先前的一個結論。

### 3.1 事實：英語的 θ 確實好聽

生成 WAV 讓使用者試聽（`reference/th-samples/`），確認：

| 樣本 | 重心頻率 | 判定 |
|---|---|---|
| `en_think.wav` | **3456 Hz** | ✅ 正確的 θ（人耳確認） |
| `en_this.wav` | **844 Hz** | ✅ 正確的 ð |

**所以引擎裏有好的 θ/ð，問題是我們取不到。**

### 3.2 為什麼取不到

**(a) 只有 `ipa` 語音接受 `[[ ]]` 音素輸入**

```
ipa     [[ t a ]]  → 16926 樣本   正常解析
en      [[ t a ]]  → 88240 樣本   ★ 失控（被當文本讀）
en-us / gmw/en / base              ★ 同樣失控
```

**(b) `ipa` 語音的音素表裏，`T` 根本不是 θ**

```
ipa [[ T ]]     重心  855 Hz   ← 不是 θ
ipa [[ D ]]     重心  871 Hz
ipa [[ s[ ]]    重心 4017 Hz   ← 最接近英語 θ
```

**(c) 語音檔裏寫 `phonemes en` 不生效**（變體是修飾符，改不了音素表）

```
ipa+thfix1 (phonemes en)   → 重心 1041 Hz   距離 0.674
ipa+thfix4 (phonemes base) → 重心  806 Hz   距離 0.668
ipa        (現用)           → 重心  855 Hz   距離 0.639
```

### 3.3 全部 209 個可用音素掃一遍：沒有免費的午餐

以英語 θ / ð 的頻譜為基準，掃過 `ipa` 語音裏全部 209 個能發聲的符號：

| 排名 | θ 候選 | 重心 | 距離 | ð 候選 | 重心 | 距離 |
|---|---|---|---|---|---|---|
| 1 | `sh.` | 4018 | 0.278 | `z[` | 1299 | 0.254 |
| 2 | **`s[`** | 4017 | **0.278** | `n.` | 383 | 0.260 |
| 3 | `sw` | 4023 | 0.279 | `h.w` | 724 | 0.262 |
| 4 | `s` | 4392 | 0.330 | `Q\` | 608 | 0.264 |

**前三名的 `sh.` / `s[` / `sw` 其實是同一個音**（重心差 6 Hz）。

> ★ **結論：目前映射表用的 `s[` / `z[` 已經是 `ipa` 語音裏能拿到的最好選擇。**
> 站點作者當初的選擇是對的 —— 不是他疏忽，是**這張表裏沒有更好的**。
> 完整結果：`reference/th-scan.json`

### 3.4 所以要整合英語的 θ，只有三條路

| 路線 | 做法 | 成本 | 風險 |
|---|---|---|---|
| **甲** | **原地補丁 `phontab`/`phondata`** —— 把 en 表的 `T`/`D` 條目搬到 ipa 表的對應槽位 | 需先解出 `phontab` 結構（已起步） | 中；字節寫錯會出怪聲 |
| **乙** | **從 `phsource` 重編譯** —— 在 ipa 表裏加 `T`/`D` 定義，`espeakedit --compile` | 需建工具鏈（wxWidgets） | 低，但要先走通流程 |
| **丙** | **旁路拼接** —— 預先用 `en` 語音渲染 θ 擦音，塞進逐字合成的音頻 | 低（不碰 espeak） | 高；合成音節裏找不到擦音位置，接縫會突兀 |

**建議**：目標是乙，甲是捷徑。丙只適合做聽感驗證。

## 三之二、路線乙：已跑通，卡在最後一步

### ✅ 成功：工具鏈建起來了，而且**不需要 wxWidgets**

原本以為要編譯 `espeakedit`（需 wxWidgets）。**其實不用** ——
真正的編譯邏輯在 `libespeak-ng/compiledata.c`，透過公開 API 暴露：

```c
espeak_ng_STATUS espeak_ng_CompilePhonemeDataPath(
    long rate, const char *source_path, const char *destination_path,
    FILE *log, espeak_ng_ERROR_CONTEXT *context);
```

於是直接用機器上已有的 **Visual Studio Community 的 `cl.exe`** 編譯，
**不用 CMake、不用 wxWidgets**（`src/windows/config.h` 是現成的）：

```
build/msvc/build.mjs      → 產生批次檔並編譯（27 個 libespeak-ng + 6 個 ucd-tools）
build/msvc/compiletool.c  → 呼叫上面那個 API 的小工具
build/msvc/out/compiletool.exe  (440 KB)
```

跑起來的結果：

```
$ compiletool.exe phsource/ out/ 22050
Compiling phoneme data: .../phsource/phonemes
Refs 5285,  Reused 4267
Compiled phonemes: 0 errors.

phondata   600,104 位元組
phonindex   48,856
phontab     64,108
```

**零錯誤。** 而且**我們編出來的 `phontab` 用上游格式解析完美自洽**
（頭 4 字節、每條目 16 字節、142 張表、剛好用完 64,108 位元組）。

### ✅ `phondata` / `phonindex` 與 WASM 格式**完全兼容**

```
              舊(WASM)                    新編譯
phondata 頭   01 48 01 00 22 56 00 00    01 48 01 00 22 56 00 00   ← 一模一樣
              version=0x014801  rate=22050
phonindex 頭  01 48 01 00 00 a1 d5 83    01 48 01 00 00 a1 d5 83   ← 一模一樣
```

（`version_phdata = 0x014801`，定義在 `synthdata.c:48`。）

### ❌ 卡點：WASM 的 `phontab` 佈局不同

```
舊(WASM)   7e 00 00 00 00 | 23 00 00 00 "base"    ← 頭 5 字節
新編譯      8e 00 00 00    | 23 00 00 00 "base"    ← 頭 4 字節
```

逐表走舊檔：表 0（`base`, 35 音素）自洽，**表 1 的表名是空的**，表 2 的 count 不合理。
窮舉（頭 4/5/6/8 × 條目 8–48 字節）**找不到任何自洽佈局**。

> **結論：這個 WASM 是從另一個 espeak-ng 修訂版編的，`PHONEME_TAB` 佈局已變。**
> 所以我們編的 `phontab` 換不進去。

### 附帶排除的兩個假設

1. **「換音素表就行」——不行。** 舊引擎認識全部 126 張表（逐個造語音檔驗證過，
   連 `base1` `base2` `consonants` 都在），但**每張表裏 `T` 的重心都是 800–1000 Hz**，
   距離英語 θ 都在 0.63 以上。`T` 是在全域被改掉的，不是某張表的問題。
2. **「θ 波形不在 phondata 裏」——不成立。** 英語語音能發正確的 θ（3456 Hz），
   說明波形在，只是**任何我們叫得出名字的助記符都取不到它**。

### 下一步

* **甲**：先確定 WASM 用的 espeak-ng 修訂版（從 `phontab` 佈局反推，或問站點作者），
  然後用那個版本重編 —— 我們的工具鏈已經現成，換個 tag 重編即可。
* **乙'**：直接換掉整個 espeak-ng WASM 構建（用我們這套能編譯的源碼），
  代價大但一勞永逸，而且**從此所有音素都可改**。
* **丙**：旁路拼接，只做聽感驗證。

> 工具都在 `build/` 與 `tools/` 下；**`engine/` 未被改動**，實驗品在 `engine-fixed/`。

### 3.5 順手澄清的兩件事

* **`T`/`D` 在 `ipa` 語音裏不是 θ/ð** —— 先前報告寫「θ 用 `T`/`D`」是看錯了行，
  實際映射用的是 `s[`/`z[`。**已更正。**
* **θ/ð 其實不算「碰撞」問題** —— 它們各自對應唯一音素，只是那個音素音質不夠好。

## 四、你列的問題音：逐條實測結果

### 3.1 先說一個好消息：映射表本身沒有「死」項

把我們用到的 **212 個助記符**全部測了一遍
（`tools/audit-mnemonics.mjs`，上下文法：`[[ <音素> a _: ]]` 對比 `[[ a _: ]]`）：

```
合計：正常 212 / 異常 0 / 失效 0
```

**沒有任何一個是「加進去等於沒加」的。** 所以問題不在映射寫錯，
而在音素本身的音質與重合。

### 3.2 頻譜實測（`tools/compare-phonemes.mjs`）

方法：取能量最高的 30 ms，24 段對數頻帶（100 Hz–8 kHz）濾波器組，
正規化後算總變差距離。**0 = 完全相同，越大越不同。**

| 問題對 | 距離 | 判定 | 與你的描述 |
|---|---|---|---|
| **d͡ʑ vs d͡ʐ** | **0.041** | ★ **幾乎完全相同** | ✅ 證實（你說「幾乎全混」） |
| ŋ vs ɴ | 0.104 | 接近 | ✅ 證實 |
| ʎ vs ɭ | 0.110 | 接近 | ✅ 大致證實 |
| ʋ vs v | 0.118 | 接近 | ✅ 證實 |
| ɹ/ɻ/ɰ vs r | 0.238 | 可分 | ⚠ 見下 |
| l vs ʎ | 0.383 | 明顯不同 | ⚠ 見下 |
| l vs ɭ | 0.392 | 明顯不同 | ⚠ 見下 |
| l vs ʟ | 0.430 | 明顯不同 | ⚠ 見下 |
| θ vs s | 0.398 | 明顯不同 | ⚠ 見下 |
| θ vs f | 0.648 | 明顯不同 | — |

各音的重心頻率（Hz），可以看出成組扎堆：

```
鼻音    N 270   n" 296   n^ 299   n 293   n. 255    ← 全擠在 250–300
邊音    l 623   l^ 664   l. 718   L[ 655   L 311
塞擦    dZ; 1809  dz. 1766   ← 幾乎一樣    dz 708   ts. 3419   ts 4703
擦音    s[ 3750   s 3835   f 2584   z[ 616   z 572
近音    r. 594    r 610    v. 272    v 396
```

### 3.3 ★ 這張表**不能**直接當結論用

**我的量測只比較「孤立音段的頻譜包絡」，捕捉不到過渡段。**

而人耳分辨**邊音、鼻音、近音**，主要靠的正是**輔音到元音的共振峰過渡**
（第二節的 `Vowelin`/`Vowelout`）。

所以：

* 「d=0.383 明顯不同」**不等於**「你聽得出區別」。
* 你說「除 l 外所有邊音幾乎不能區分」很可能是對的 ——
  問題出在**過渡段一模一樣**，而不是孤立頻譜。
* **你的耳朵仍然是唯一裁判。**

要把這一類問題坐實，得改成分析**「輔音+元音」整個音節的過渡軌跡**（F2 locus 之類）。
這個工具我還沒寫。

## 五、兩類問題，修法完全不同

### 類型甲：頻譜上就重合（**必須改音素定義**）

| 音 | 現用 | 實測 |
|---|---|---|
| **d͡ʑ / d͡ʐ** | `dZ;` / `dz.` | 距離 0.041，重心 1809 / 1766 Hz，**樣本數 13352 / 13344** |
| **ŋ / ɴ** | `N` / `n"` | 距離 0.104，重心 270 / 296 Hz |
| **ʋ / v** | `v.` / `v` | 距離 0.118，重心 272 / 396 Hz |
| **ʎ / ɭ** | `l^` / `l.` | 距離 0.110 |

這一類**換映射沒用** —— 引擎裏根本沒有第二個夠不同的音可換。
要嘛改 `phondata`，要嘛接受。

### 類型乙：孤立頻譜有差，但聽感不分（**可能改過渡段就夠**）

邊音、鼻音、近音多屬此類。修法是改 `phsource` 裏的
`Vowelin` / `Vowelout`，**不必動共振峰本體**。
這比造新音素容易得多。

### 類型丙：完全缺失（**要從無到有造**）

`ɟ` `ʙ` `ɜ` `ɞ` `ɶ` `ɘ` `ʜ` `ʢ`
—— 這些目前是撤除 / 未採用狀態。

### 已確認「不是問題」的

那 40 組「碰撞」裏**大部分是同一音的不同寫法**：

```
ts.  ← t͡ʂ tʂ ʈ͡ʂ ʈʂ        ← 同一個音的四種寫法
N    ← ŋ ŋ̩ ng
i    ← i z̩ ĭ
```

**不需要修。**

## 六、三條路線

### 路線 A：量化「過渡段」差異，先看清楚類型乙到底有多嚴重

* 工具：分析「輔音 + 元音」音節的 **F2 過渡軌跡**。
* 產出：一張「哪些音在過渡上真的沒區別」的表。
* 成本：低（改改現有 `compare-phonemes.mjs`）。
* **建議先做這個** —— 它會告訴你類型乙的實際規模，直接決定值不值得建工具鏈。

### 路線 B：原地補丁 `phondata`

* 解出 Wcmd 位元組碼（格式在 espeak-ng 的 `wavegen.cpp`，約 40 條指令）。
* **保持大小不變 → JS 與 wasm 都不用改。**
* 前置：寫 Wcmd 解碼器。工作量中等但邊界清楚。
* 風險：解碼錯誤會產生怪聲，需要逐個試聽。

### 路線 C：從 `phsource` 重新編譯（**最乾淨，也最貼合你的設想**）

1. 取 espeak-ng 源碼樹（含 `phsource/`）
2. 編譯 `espeakedit`（需 wxWidgets，MSYS2 下 `pacman -S mingw-w64-x86_64-wxwidgets`）
3. 改 `phsource/` 裏的音素定義（`F1= F2= F3=`、`Vowelin`、或換 WAV）
4. `espeakedit --compile` → 新的 `phondata`
5. 重打包 `.data`（更新 JS 裏的偏移表）

* **每個音素的邊際成本最低**，可重複、可版本化。
* 前置成本最高（工具鏈）。
* 改 WAV（θ 這類）比改共振峰**更直接**，也更容易做好。
* ⚠ espeak 的共振峰模型有固定框架，光改共振峰不一定能做出滿意的音 ——
  **最終仍只能靠耳朵判**。

**路線 C 適用於類型甲、乙、丙全部**；路線 B 只適合小修。

## 七、已知的量測陷阱（五次踩坑記錄）

做這件事之前必須先把量測做對，否則會得出**錯誤結論**。
以下四次都是我實際踩過的：

1. **只看振幅包絡** → 清濁、頻譜差異全丟，`T` 與 `D` 被判成同一個。
2. **取信號中段** → 輔音短、後面接着 `_:` 停頓，中段幾乎全零，
   重心算出 0 Hz，**所有輔音被判成同一個**。
3. **孤立測清塞音** → `p` `t` `k` 孤立時就是「靜默 + 極短爆破」，
   被判成「無輸出」。**必須用 `[[ <音素> a _: ]]` 這種上下文**。
   同理，鼻音孤立時樣本數反而比停頓**少**，
   拿「樣本數變多」當判據也會誤判。
4. **測了不存在的助記符** → 我用大寫 `R` 測 `ʀ`，得出「無輸出」的結論；
   實際映射用的是 `r"`，**完全正常**。這是假警報，已撤回。

**教訓：在把任何「某音素不行」寫進結論之前，先確認量測方法本身是對的。**

---

## 八、建議的推進順序

1. **先做路線 A**（過渡段量測）—— 半天，零風險。
   它會告訴你類型乙的規模，直接決定後面值不值得做。
2. **同時驗證路線 C 的工具鏈**：先不動任何音素，只走一遍
   「取源碼 → 編譯 → 得到 `phondata` → 替換 `.data` → **確認發聲與原來完全一致**」。
   **這一步走通，後面才有得談。**
3. 工具鏈通了之後，挑**一個**音做端到端試點。
   建議挑 **θ**（走 WAV 路線，最直接）或 **d͡ʑ/d͡ʐ**（問題最明確）。
4. 試點滿意再批量做。

---

## 九、參考音頻的來源與注意

* 候選：Wikipedia IPA chart 錄音（CC 授權）、各種 IPA reader、大學語音學課程示範。
* **授權要看清** —— 若成品要發佈，採樣來源必須可再分發。
* **元音 / 響音**：量共振峰即可（`praat-parselmouth` 或用 LPC 自己算）。
* **清輔音**：**不需要扒共振峰** —— 直接找一段乾淨的目標音採樣，
  裁成 22kHz/16bit 單聲道就能餵給 `WAV()`。
  ⚠ 但要注意與 espeak 現有採樣的**響度與音色一致性**，
  否則單個音素會突兀。
